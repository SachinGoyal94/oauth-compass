# Airtable OAuth App Setup Guide

Airtable uses a self-service OAuth registration model with no formal approval process. Register at https://airtable.com/create/oauth, configure redirect URI and scopes, generate a client secret (shown once), and optionally add support email, privacy policy, and terms of service URLs to share with external users. PKCE (S256) and state parameter are mandatory. Tokens expire in 60 minutes; refresh tokens last 60 days. Enterprise admins can block integrations.

## Difficulty & time

Self-service registration, no approval wait; minimal friction for developers

- **Difficulty:** Light (2/5)
- **Hands-on setup:** 15-30 minutes
- **Approval wait:** None

## Prerequisites

- **Required:** Airtable account — Must have an Airtable account to access the Builder Hub and register OAuth integrations
- **Required:** HTTPS redirect URI — Valid HTTPS redirect URI (localhost allowed for development); exact match required
- Optional: Support email, Privacy Policy URL, Terms of Service URL — Required only if sharing the integration with other Airtable users; missing fields block external users with access_denied
- **Required:** Server-side secret storage — Client secret shown once at generation; must be stored securely for token exchange

Navigate to the direct OAuth registration URL or access via Builder Hub (Profile icon → Builder Hub → Development → OAuth integrations)

Click 'Register new OAuth integration', provide a unique integration name and a valid HTTPS redirect URI (localhost allowed), then click 'Register integration'

### 3. Configure permission scopes (Integration management page (after registration))
Select at least one permission scope from available categories: data.records:read, data.records:write, schema.bases:read, schema.bases:write, user.metadata:read, webhooks:manage
*[~2 minutes, human step; evidence: verified_from_docs]*
> Scopes are space-delimited in authorization requests; choose minimal required scopes

### 4. Generate and save client secret (server-side apps) (Integration management page)
Click to generate Client Secret; copy and store it immediately — it is shown only once and cannot be recovered
*[~1 minute, human step; evidence: verified_from_docs]*
> Generating a new secret invalidates the previous one and breaks existing auth flows until code is updated

### 5. Add sharing metadata (required for external users) (Integration management page)
Fill in Support Email, Privacy Policy URL, and Terms of Service URL; click 'Save changes'
*[~2-5 minutes, human step; evidence: verified_from_docs]*
> Missing any of these three fields causes access_denied for all non-developer users

### 6. Implement OAuth 2.0 authorization request with PKCE (Application code)
Redirect user to https://airtable.com/oauth2/v1/authorize with parameters: client_id, redirect_uri, response_type=code, scope (space-delimited), state (cryptographically random), code_challenge (base64url SHA256), code_challenge_method=S256
*[~10-20 minutes, agent-automatable; evidence: verified_from_docs]*
> PKCE (S256) is mandatory; state parameter required for CSRF protection; code challenge must be base64url-encoded SHA256 of code_verifier

### 7. Exchange authorization code for tokens (Application backend)
POST application/x-www-form-urlencoded to https://airtable.com/oauth2/v1/token within 10 minutes with code, grant_type=authorization_code, redirect_uri, code_verifier; include Authorization: Basic base64(client_id:client_secret) header if client secret exists
*[~5-10 minutes, agent-automatable; evidence: verified_from_docs]*
> Token response includes access_token (opaque Bearer), refresh_token, token_type='Bearer ' (trailing space), expires_in=3600, refresh_expires_in=5184000

### 8. Implement token refresh logic (Application backend)
POST to https://airtable.com/oauth2/v1/token with grant_type=refresh_token, refresh_token, optional scope subset; handle 409 Conflict if refresh attempted too rapidly; store new tokens (previous access and refresh tokens are invalidated on each refresh)
*[~10-15 minutes, agent-automatable; evidence: verified_from_docs]*
> Refresh tokens expire after 60 days of inactivity; auto-refresh well before expiry; rate limit <10 requests/second per token (excess leads to revocation)

## Gotchas

- **Client secret shown once only** — Lost secret cannot be recovered; regenerating breaks all existing auth flows until application code is updated
  - Handle: Copy immediately upon generation; store in secure secret manager; plan secret rotation carefully
- **Redirect URI exact match required** — Authorization fails silently (no error) if redirect URI does not exactly match the registered value
  - Handle: Copy/paste from console; test with exact string including trailing slashes; use HTTPS in production
- **Missing ToS/Privacy/Support email blocks external users** — All three fields are mandatory for sharing; absence returns access_denied for every non-developer user
  - Handle: Fill all three before distributing integration; verify URLs are accessible
- **Generating new client secret breaks existing flows** — All pending authorizations and token exchanges using the old secret fail immediately
  - Handle: Coordinate secret generation with code deployment; update secret in all environments simultaneously
- **Refresh token expires after 60 days inactivity** — User must re-authorize if refresh token expires; no programmatic recovery
  - Handle: Implement proactive refresh well before 60-day window; monitor token age
- **PKCE (S256) and state parameter are mandatory** — Authorization request fails without PKCE; missing state exposes CSRF vulnerability
  - Handle: Generate cryptographically random code_verifier per request; compute code_challenge as base64url SHA256; include state
- **Enterprise admin can block integration** — Enterprise customers may restrict third-party integrations, causing access_denied outside developer control
  - Handle: Handle access_denied gracefully; inform users to contact their admin; cannot be resolved by developer
- **Rate limit on token refresh (<10 req/sec per token)** — Exceeding limit causes token revocation; 409 Conflict if refresh attempted too rapidly
  - Handle: Implement exponential backoff; serialize refresh requests per token; cache valid access tokens

## Common blockers

- **Enterprise admin blocks integration** — Cannot be resolved by developer; user must request admin to allow the integration in enterprise settings
  - Escalation: User contacts their Airtable enterprise administrator
- **Client secret lost or compromised** — Generate new secret in console and update all application environments immediately; existing tokens remain valid until expiry
  - Escalation: None; self-service in console
- **Redirect URI mismatch** — Verify exact string match in console and authorization request; update console if URI changed
  - Escalation: None; self-service in console
- **Missing sharing metadata (support email, privacy policy, terms)** — Add all three URLs in integration management page and save changes
  - Escalation: None; self-service in console
