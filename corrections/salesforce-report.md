# Salesforce OAuth Setup Guide (v1) — Human Verification Report

Verified 2026-11-04 against official Salesforce Help (help.salesforce.com) and Salesforce Developer documentation (developer.salesforce.com) only. Draft: `knowledge/guides/drafts/salesforce/v1.md`. Corrections applied: `corrections/salesforce.json`.

## Confirmed

These draft claims were re-checked against official pages and stand as written (source URLs in the draft are valid and support the claims).

- **Connected App creation is restricted as of Spring '26.** "Connected apps creation is restricted as of Spring '26... we recommend using external client apps instead. If you must continue creating connected apps, contact Salesforce Support." Creation is blocked through both UI and Metadata API (package installation excepted); existing connected apps keep working, including editing, installation, and deletion. (Help: Create a Connected App; KA 005228017)
- **ECAs are the path for new integrations.** "New integrations must use ECAs instead of Connected Apps" (KA 005318040); "As of Spring '26, new Connected Apps cannot be created... For new integrations, partners must use an ECA" (KA 005387798); "External client apps are the new generation of connected apps" (CA vs ECA comparison).
- **The four security controls and the May 11, 2026 deadline.** OAuth PKCE, Refresh Token Rotation, Refresh Token Idle TTL (30-day), and Refresh Token IP Allowlist — each with "Compliance Due Date: May 11, 2026" (ISVforce "Secure Your Connected Apps and External Client Apps"; KA 005387798).
- **In-scope criteria for the deadline.** Applies to apps the partner owns (config lives in their DevHub/namespace/packaging org) **and** that are "in use by more than two customer production orgs." Single-customer-org apps and customer-created apps for their own use are out of scope (adoption still recommended).
- **Locking via 'Review Controls' is irreversible.** "Clicking the 'Review Controls' link permanently locks these security controls... once locked, they cannot be unlocked or reverted." Test in a sandbox first; you can preview idle-TTL behavior by manually revoking an access token. (KA 005387798)
- **RTR mechanics.** With RTR on, each refresh call issues a new refresh token and invalidates the old one; reusing a rotated-out token returns `invalid_grant` and also invalidates the current refresh token and associated access tokens — shared token copies across systems will conflict. (Enable OAuth Settings help; KA 005387798)
- **Refresh Token IP Allowlist limit of 10,000 total IPs.** "A total of 10,000 IP addresses are allowed across all configured ranges... a firm requirement and is unable to be extended" (raised from 256 per the article's Sep 23, 2026 change log). Exemptions: end-user device flows with custom URI schemes, and Salesforce-to-Salesforce refresh token flows. Allow 30–45 minutes for new ranges to propagate before enabling.
- **Callback URL rules.** The redirect URI "must match one of the values" registered in Callback URL or approval fails; "the URL must use secure HTTPS or a custom URI scheme"; multiple URLs allowed, 2000-character cumulative limit; `http://localhost:1717/OauthRedirect` is the documented dev example. (Enable OAuth Settings help; SFDX Dev Guide)
- **Scopes.** `api` + `refresh_token, offline_access` is the right minimal set for API integrations; `refresh_token` and `offline_access` are officially synonymous; `full` "encompasses all other scopes" and "doesn't return a refresh token"; Security Review requires written justification for `web`/`full`. (OAuth Tokens and Scopes; Mobile SDK Scope Parameter Values; KA 005318040)
- **2GP packaging requirements for distribution.** Packaging is mandatory when the ISV controls the callback URLs, uses its own client credentials/JWT certificate, or ships a canvas app; "CAs and ECAs should be packaged for distribution on AppExchange"; local ECAs are not copied to sandboxes on clone/refresh. (KA 005318040; External Client Apps help)
- **Security Review submission materials.** CA/ECA usage disclosure, secrets-management documentation, credentials for all integrations, and for packaged ECAs "share the client key in the submission documents only — don't share the client secret." (KA 005318040)
- **'Manage External Client Apps' permission.** "To deploy ECA metadata via SFDX or the Metadata API, your deployment user or service principal must be granted the Manage External Client Apps permission." (KA 005228017)
- **OAuth endpoint paths.** Authorization `/services/oauth2/authorize` and token `/services/oauth2/token`; `https://login.salesforce.com/services/oauth2/authorize` is the documented example form (Mobile SDK "Configure a Salesforce Authentication Provider"; Web Server Flow help). Resolves the draft's "endpoints assumed" unverified item.
- **Free apps pay no Security Review fee.** "If you plan to distribute your solution for free, you don't pay the fee." (ISVforce, How the Security Review Works) — resolves another draft unverified item.
- **$999 fee exists.** "May require a security review submission fee of $999. Please work with your PAM to confirm" (KA 005387798) — but see the wording correction below.

## Corrected

1. **Most important — the guide conflates "any OAuth integration" with "AppExchange ISV distribution."** DevHub/PBO, 2GP managed packaging, the four security controls deadline, and AppExchange Security Review are distribution-path requirements only. For connecting your own org (the Composio use case), you create a **local** ECA in Setup → App Manager — no packaging, no review, no DevHub — and the May 11, 2026 partner deadline explicitly does not apply to customer-created apps ("Connected Apps created by customers for their own use are not in scope"). Corrected: summary, difficulty (4 → 2, "Heavy review" → split wording), time, prerequisites (DevHub/PBO and SFDX/2GP made conditional), steps 1, 6, 7, blocker 3.
2. **Wrong navigation path in step 2.** "Setup → External Client Apps → New" is not the documented path. Official steps: "From the Quick Find box in Setup, enter App Manager... Click New External Client App" (SFDX Dev Guide, "Create an External Client App in Your Org").
3. **False "displayed only once" secret claim (step 4 and agent_vs_human).** The consumer key and secret can be retrieved later — External Client App Manager → your app → Settings → OAuth Settings → "Consumer Key and Secret" (with identity verification), or App Manager → View → "Manage Consumer Details" — and can be rotated. The draft's "Client secret cannot be retrieved later" is wrong; keep the store-securely advice.
4. **Review timeline "4-9 weeks" not supported.** Official estimates: 1–2 weeks submission verification + 3–4 weeks first-time Product Security testing (~4–6 weeks total); resubmissions 2–3 weeks (ISVforce, How the Security Review Works). Corrected in time and step 7.
5. **Fee wording tightened.** Official text says a $999 submission fee *may* apply and to confirm with your PAM; it does not say "$999 per attempt" or that resubmission is charged again — moved the resubmission-fee claim to unverified. "Free apps may have fee waived (criteria unverified)" is now resolved: free distribution pays no fee.
6. **Removed "Idle TTL enforcement effective November 2026" (step 5 nuance).** No official page mentions November 2026; all four controls carry the May 11, 2026 compliance due date. Replaced with verified mechanics: sliding 30-day window, Metadata API deactivation caveat, IP-range updates after locking.
7. **5-grants gotcha re-worded to match docs.** Official: "The default is five authorizations per external client app per user. If a user tries to grant access... after reaching the org's limit, the access token that has been **unused for the longest period of time** is revoked." The draft's "invalidates the oldest" and "multiple sign-ins (even same device) increment count" were not supported (latter removed); source corrected to the OAuth Authorization Flows page (draft cited KA 005387798, which doesn't contain this limit).
8. **Gotcha 1 date parenthetical fixed.** "(Spring '26 (Oct 2026))" conflated the article's Oct 7, 2026 publish date with the release; the restriction began **with the Spring '26 release**. Also added the verified nuance that editing/installing/deleting existing apps is unaffected and that EOS timing is unannounced.
9. **Step 7 scan list corrected.** Removed "DAST" (not listed on the ISVforce pages reviewed); kept Salesforce Code Analyzer and Source Scanner (Checkmarx). Also removed the ">2 customer prod orgs" mis-attribution to KA 005318040 — the in-scope criteria (own the config AND >2 customer production orgs) are defined in KA 005387798 / the ISVforce controls page.
10. **Step 5 augmented with a missing verified gotcha.** "Updating the Connected App (CA)/ECA configuration using the Metadata API will de-activate both the RT Idle Token and RT IP Allowlist settings" unless the controls are activated and locked — highly relevant to the agent-automatable packaging/deployment step.
11. **Source list cleaned.** Draft's `what_it_supports` for KA 005318040 wrongly claimed it documents "fees ($999/attempt), in-scope criteria (>2 customer prod orgs)" — both live in KA 005387798 / ISVforce guide. Added the official pages that actually verify callback rules, scopes, ECA creation, endpoints, and the CA/ECA feature comparison (17 official sources, max respected).

## Could not verify

- Whether resubmission of a failed Security Review incurs **another $999 fee** (official pages state the fee "may" apply and resubmissions take 2–3 weeks; per-attempt charging is not stated).
- Exact **End-of-Support timeline** for existing Connected Apps — "Salesforce will be announcing End-of-Support (EOS) soon"; no date published.
- Removal date of the Support-enabled "Allow creation of connected apps" workaround — "In future releases, Salesforce Support won't be able to enable the creation of new connected apps"; no specific release named.
- Whether **DAST** scan reports are required — required scans "depend on the architecture of your solution"; the pages reviewed itemize Code Analyzer and Source Scanner only.
- **Composio-specific behavior** (non-Salesforce, out of scope for official-doc verification): exact managed OAuth callback URL format and whether Composio handles PKCE/RTR automatically for Salesforce. Kept as "reported" with a confirm-with-Composio note.
- The draft's "Idle TTL enforcement effective November 2026" — could not be found or corroborated anywhere in official documentation; treated as incorrect and removed rather than left unverified.

*Verification method: pages read in a rendered browser session on 2026-11-04 (help.salesforce.com Lightning Help, developer.salesforce.com docs, and the three numeric Knowledge Articles). No non-Salesforce source was used for any fact.*
